numo-jamezz-bridge — build context
You are building a payment/ordering bridge. This document is the source oftruth for scope, contracts, and behavior. Implementation details (exactlibrary versions, file structure within a variant, naming) are yours tochoose using current best practices — but the API shapes, state machine,data model, and acceptance criteria below are binding.

What this is
A customer scans a QR code at a burger restaurant table, orders on theirphone, pays with Bitcoin Lightning, and receives an order confirmationnumber to quote at the counter. Behind the scenes:

QR encodes https://order.<domain>/t/<tableId> served by this bridge.
Menu comes from Jamezz (the platform running the restaurant'swebshop — BurgerMeister), which holds a saved Visa card on file.
That Visa card is a 2fiat virtual card funded via Lightning.
On checkout the bridge requests a funding invoice from 2fiat for theorder total + margin; the customer pays it from any Lightning wallet;the card gets credited.
The bridge places the order at Jamezz via their shop/API using thesaved card, and shows the customer the Jamezz order confirmation number.
Money flow: customer sats → 2fiat card → Jamezz charge → merchant.The bridge never custodies funds. Nothing is ever sent to a kitchen —Jamezz is the kitchen.

Facts you can rely on (from the product owner)
2fiat programmatic top-ups already work. The owner has working codeand will paste it into the real client later. Build a clean stub with thedocumented contract and a TODO marker; do not invent 2fiat API endpoints.
Jamezz recon is pending (Playwright capture of a manual checkout).Their shop may expose a JSON API or only HTML forms. Same approach:stub with the contract, TODO marker, no invented endpoints.
This is a POC: single venue, one shop account, one card, no useraccounts, no multi-tenancy, no automated customer refunds (failures alerta human — see Runbook section).
Golden rules — never violate
Bridge never holds customer funds (Mode A: invoices fund the card directly).
Server-side pricing only — clients send {itemId, qty}; totals arecomputed from the live Jamezz menu. Never trust a client-sent amount.
Persist the pending order before showing the payment invoice.
Every Jamezz placement attempt is preceded by a lookup of the order'spickup reference (exactly-once guard — see below).
Never trust settlement webhooks — always re-verify invoice status with2fiat before acting.
Every state transition writes a row to the ledger table.
DEV_MODE must be off in production; dev-only endpoints 404 without it.
Mock modes must make the entire flow testable with zero externalservices (this is how acceptance is verified).

State machine (binding)
created → awaiting_payment → funding_settled → placing → confirmed                ↓ (invoice expired unpaid)         ↓ (failure)              failed  ←────────────────────────── failed
awaiting_payment: invoice issued, shown to customer, has expiry.
funding_settled: 2fiat confirmed settlement (verified, not just claimed).
placing: calling Jamezz to place + pay the order.
confirmed: Jamezz order number stored.
failed: terminal for this order; includes error text.
Revive path: if settlement arrives for an order alreadyfailed("invoice expired unpaid"), transition back tofunding_settled (money moved — proceed). Log it distinctly in the ledger.
Placement retries: backoff, max 5 attempts, then failed + alert.
Idempotency: duplicate settlement webhooks must be no-ops.
Data model (binding)
CREATE TABLE orders (  id TEXT PRIMARY KEY,                -- UUID generated by the bridge  table_id TEXT NOT NULL,  status TEXT NOT NULL DEFAULT 'created',  total_minor INTEGER NOT NULL,       -- NOK øre, from Jamezz menu  charge_minor INTEGER NOT NULL,      -- total + margin (what we invoice)  invoice_id TEXT UNIQUE,  invoice_bolt11 TEXT, invoice_sats INTEGER, invoice_expires_at INTEGER,  pickup_ref TEXT NOT NULL UNIQUE,    -- "BRIDGE-<8 hex of uuid>" — dedupe key  confirmation_number TEXT,           -- Jamezz order number, e.g. "JM-1042"  error TEXT,  attempts INTEGER NOT NULL DEFAULT 0,  created_at INTEGER NOT NULL, updated_at INTEGER NOT NULL);CREATE TABLE order_items (  order_id TEXT NOT NULL, item_id TEXT NOT NULL, name TEXT NOT NULL,  qty INTEGER NOT NULL, unit_minor INTEGER NOT NULL);CREATE TABLE ledger (                 -- one row per state transition  id INTEGER PRIMARY KEY AUTOINCREMENT, ts INTEGER NOT NULL, order_id TEXT,  from_status TEXT, to_status TEXT, ln_invoice_id TEXT, twofiat_id TEXT,  jamezz_order_no TEXT, sats INTEGER, nok_minor INTEGER, note TEXT);
All money in integer minor units (NOK øre). Timestamps as epoch ms.On D1, status transitions (UPDATE + ledger INSERT) must be atomic — usedb.batch(). On SQLite, same via transaction.

Cross-cutting behavior (binding)
Margin: invoice amount = menu total + MARGIN_PCT (default 2%),margin rounded up to a whole krone. Rationale: absorbs 2fiat fees +FX spread; residue rolls into card buffer.
Exactly-once placement: before every placeOrder, callgetOrderByRef(pickupRef); if found, mark confirmed with that number.The pickup reference must be searchable at Jamezz (goes in the pickupname field).
Webhook verification: always call getInvoiceStatus after receivinga webhook; only act on verified "settled".
Alerts: on any failed-after-paid order and on stuck orders, POST{text: message} to ALERT_WEBHOOK_URL (if set). Alerting must neverbreak request handling. At minimum log loudly.
Cron (Worker variant), 1/min: (a) poll unsettled invoices and runsettlement if 2fiat has no webhook; (b) expire awaiting_payment pastinvoice_expires_at → failed("invoice expired unpaid") + alert;(c) retry stuck funding_settled orders.
Loop (node variant), ~2s: same three jobs, finer granularity.
